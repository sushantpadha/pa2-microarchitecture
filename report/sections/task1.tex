\task{1}{Stride Pattern Prefetching}

\subsection{Task 1A: IP-stride prefetcher}
We went through and understood the IP Stride prefetcher implementation provided in the GitHub repository.
It holds 24 fully-associative LRU IP Trackers with a prefetch degree of 3 (limited within a page boundary). Only the last 8 bits of IP are used in the trackers. Once a particular stride happens two times in a row, it starts prefetching data.

\subsection{Task 1B: Design}

The prefetcher (\texttt{prefetcher/spp.l1d\_pref}) sits at the L1D and works on the cache-line strides of each load IP. It never prefetches outside the 4\,KB page of the access that triggers it. It has three tables:
\begin{enumerate}
  \item an \textbf{IP table} (16 sets $\times$ 6 ways, LRU) that holds each tracked IP's uniform stride and stride signature,
  \item a \textbf{pattern table} (512 entries, direct mapped) from a signature to the stride that followed it,
  \item a \textbf{recent-prefetch filter} (256 entries, direct mapped) that drops repeat requests and measures accuracy.
\end{enumerate}

\textbf{IP table:} An IP gets an entry on its first L1D miss. Once tracked, it trains on every load. Each entry keeps the low 16 bits of the IP's last line address, its last stride with a 2-bit confidence that helps to predict the next line on uniform stride mode, a 9-bit stride signature that has information of the past 3 stride length at this IP, and a 2-bit chooser a saturated counter to make sure switches are not too often. A stride larger than 63 lines always leaves the page, so it resets the entry's stride state.

\textbf{Two Dynamically Chosen Predicors (Per IP):} For each new stride $s$:
\begin{itemize}
  \item \emph{Uniform}: remember the last stride and predict that it repeats. Its confidence goes up when it repeats and down otherwise. The stored stride is replaced only at confidence 0, so one stray stride does not reset a stable one.
  \item \emph{Pattern}: predict the stride based on the stride history. Storing the last few strides of every IP, and a map from each history to its next stride, would be too large. Instead the history is hashed into a 9-bit signature, $\textit{sig} \leftarrow (\textit{sig\_old} \ll 3) \oplus s$, with $s$ as 7-bit two's complement. Each new stride moves the older ones 3 bits up, so the signature covers the last 3 strides: the newest in 7 bits, the one before in 6, the one before that in 3. 2-3 different singature were tested with differing shift and size but no observable change was seen.
\end{itemize}

A 2-bit chooser per IP starts at ``uniform'' and moves one step toward the predictor that was right whenever exactly one of them was. The uniform prediction is used when it is confident (confidence $\ge 2$) and the chooser is in its upper half, or when the pattern table has no confident prediction. Otherwise the pattern prediction is used. So uniform strides have priority, and an IP falls back to the pattern table only after the pattern table has been right where the uniform stride was wrong.

\textbf{Pattern table:} The 9-bit signature indexes the 512 entries directly. They are shared by all IPs. Each holds a 7-bit stride and a 2-bit confidence. This is the next-stride predictor based purely on the history independent of the IP, reasoning being that storing a pattern table for each IP is too expensive in terms of space.

\textbf{Issuing:} The chosen predictor is walked ahead \emph{degree} steps: $L+s, L+2s, \dots$ for a uniform stride. For a pattern, each predicted stride is shifted into a copy of the signature to look up the next one. The walk stops at the first line outside the page, or at a pattern-table entry without confidence. A prefetch fills the L1D unless half of the L1D MSHRs are busy. In that case it fills only the L2 Cache. This make sure that the prefetch doesnt bottleneck the demand misses.

\textbf{Recent-prefetch filter (RPF):} The RPF holds the lines requested recently, indexed by the low 8 bits of the line address with a 10-bit tag. Once a Hit is found the entry is removed so that multi-hit line dont inflate the accuracy. It also records whether each request has filled the L1D, which the accuracy checker uses (see Subsection \nameref{ssec:AccuracyThrottling}).

\subsection{Accuracy throttling}\label{ssec:AccuracyThrottling}

\textbf{Accuracy checker:} The RPF records whether each requested line has filled the L1D.
\begin{itemize}
  \item A prefetch is counted as issued once it fills the L1D.
  \item It is useful if a demand load reaches the line while the line is still in the RPF.
  \item A demand that misses on a requested line that has not filled yet is a late (or L2-only) prefetch. The prediction was right, so it counts as both issued and useful.
  \item A demand that hits on a requested line that never filled means the line was already cached. That prefetch was redundant and is not counted.
\end{itemize}
A prefetch that fills only the L2 is counted only if a demand reaches it, so an unused one is not seen.

\textbf{Degree control:} The degree is \textbf{not} fixed. It is chosen at run time. Every epoch of 256 counted prefetches, accuracy $a = \textit{useful}/\textit{issued}$ is compared with two thresholds. The degree goes up by one if $a \ge 0.75$, down by one if $a < 0.50$, and otherwise stays. It ranges from 1 to 8 and starts at 4. The degree the throttle settles on differs by trace:

\begin{center}
\includegraphics[width=0.6\textwidth]{t1_degree.png}
\end{center}

Trace2, where SPP is most accurate, spends the most epochs at the cap of 8. Traces 1 and 3 spend most at degree 4.

\textbf{Why these thresholds:} $T_\text{low} = 0.5$ is the break-even point: below it, most prefetches are useless. $T_\text{high} = 0.75$ leaves a gap so the degree does not oscillate. Sweep (default starred):

\end{center}

Speedup is flat (1.0149--1.0167); the default is within 0.0002 of the best and, of those, issues the fewest useless prefetches.
